# 別セッション分析依頼パッケージ (テンプレ)

別のモデル/セッション (例: Fable、Codex) に「困ったこと」の分析を持ち込むときに、依頼側 (例: Opus) が埋めるテンプレ。**目的は、分析役が依頼側の解釈を経由せずに生データから独立に考えられるようにすること** — 結論やまとめを渡すと分析役が同じバイアスを継承する。

運用: 埋めたものを #212 (現行 tracking issue) にコメントとして投稿し、分析役セッションには「#212 の最新コメントの分析依頼を見て」とだけ伝えれば開始できる (このプロジェクトの記録一本化と同じ流儀)。チャット貼り付けの断片でセッションを跨がない。

---

## 1. 状況 (3 行以内)

- 何をしようとして / 何が起きて / 何が期待と違うか。**解釈は書かない** (「〜が壊れたと思う」ではなく「〜というコマンドが〜を出力した」)

## 2. 再現の pin (分析役が同じものを再現できる最小情報)

- commit hash: `git log --oneline -1` の出力そのまま (branch 名も)
- 実行コマンド: コピペで再現できる完全形 (環境変数 `KALIMBA_SETTINGS_OVERRIDES` 等・作業ディレクトリ込み)
- 対象: tx id / fixture 名 / テスト名 / 録音の権利区分 (local-only 依存があるなら明記 — 分析役の環境で再現可能かに直結)

## 3. 生データ (加工・要約しない)

- コマンドの生出力 (エラーなら traceback 全文。長ければ gist やファイルパス)
- 関連する機械出力のパス: dual-run / benchmark_history.jsonl の該当行 / fn-taxonomy / debug payload の保存先
- 数値の変動が問題なら: **変動前後の両方の値 + それぞれの測定日時 + 測定時の commit**。headline なら分母 (n=X / current・frozen・CI gate のどれか) を必ず添える

## 4. 時系列の切り分け

- 最後に正常だった時点 (commit / 日時) と、その確認方法
- その間に入った変更の範囲: `git log --oneline <good>..<bad>` の出力

## 5. 既に試したこと (事実として)

- 試した仮説 → 検証コマンド → 生の結果、の組で列挙 (「ダメだった」ではなく出力を貼る)
- 未検証の仮説があれば「未検証」と明示して分離

## 6. 既知の罠チェック (該当するものを実施済みにしてから持ち込む)

- [ ] in-process 診断の dedup 汚染を排除した (直 POST は 2 回目が汚染される — dryRun+force か nfb.transcribe_payload 経由。memory/設計 doc §9.5 の既知罠)
- [ ] headline の分母と系 (current benchmark / S7 frozen / CI repo gate) を取り違えていない (sprint-plan-2026-07d「数値 authority」節)
- [ ] dev サーバーは 8001 (8000 は prod 占有)、実験は `KALIMBA_DATA_DIR` 隔離
- [ ] fixture への影響評価は実 pytest (ad-hoc の event count 比較は偽回帰を出す)
- [ ] キャッシュの由来を確認した (score_alignment_diagnosis は recognizer fingerprint で自動 invalidate)

## 7. 分析してほしい問い (1〜3 個、明確に)

- 例:「この FP 3 件は同一機構か別機構か」「この数値変動は実回帰か分母変化か」— open-ended な「どう思う?」は避け、判定可能な問いにする

## 8. (行動系の問題のみ) セッション経緯

依頼側エージェント自身の行動が問題 (自走が止まる・方向がずれる・委任失敗) の場合:

- ユーザーが与えた指示の原文
- それに対して実際に取った行動の時系列 (要約可、ただし判断分岐点は正確に)
- 期待した行動との差
- → 分析役の出力は「プロンプト/運用調整の提案」になり、[[model-roles-third-term]] memory の調整節に反映する

---

**分析役側の規律** (依頼を受けた側が守ること): 生データから独立に仮説を立ててから依頼側の「試したこと」と突き合わせる (逆順にしない)。結論には確度 (A-D) と根拠 commit/測定を付す。修正の実行は依頼側セッションの担当 — 分析役は所見までで、直接 main を触らない (explorer 規範と同型)。
