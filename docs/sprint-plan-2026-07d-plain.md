## 0. まず、このプロジェクトは何をしているのか

**カリンバの演奏を録音すると、自動で楽譜になるソフト**を個人で開発しています。最終目標は「何を弾くか事前に知らせなくても、自由に弾いた演奏がそのまま楽譜になる」ことです。

開発は、人間 (開発者) と AI アシスタントの共同作業で進んでいます。AI がプログラムの作成・実験・測定のほとんどを行い、人間は「方向を決める」「演奏を録音する」「耳で聴いて正解を確定する」「大事な節目で進めてよいか判断する」という、人間にしかできない仕事を担当します。

作業は「期」という大きな区切りで進めており、いま第 3 期が終わって**第 4 期**が始まるところです。この文書は第 4 期に「何を・どの順番で・どんなルールで」やるかの計画書です。

## 1. 用語辞書

本文を読む前にざっと眺めてください。本文中でも初出時にはなるべく説明を添えています。

### 音・カリンバの言葉

| 用語 | 意味 |
|---|---|
| **tine (ティネ)** | カリンバの金属の鍵 (弾く棒) 1 本 1 本のこと。 |
| **17-C / 34L-C / G-low** | カリンバの機種名。17-C = 17 鍵のハ長調、34L-C = 34 鍵で半音も全部出せるタイプ (表と裏の 2 列)、G-low = 17 鍵の低いト長調。 |
| **onset (オンセット)** | 音の弾き始めの瞬間。楽譜化ではまず「いつ弾いたか」を見つけることが出発点になります。 |
| **倍音 / partial (パーシャル)** | 1 本の鍵を弾くと、基本の音の高さ以外に、より高い成分も同時に鳴ります。これが倍音です。カリンバの倍音はピアノなどと違い、きれいな整数倍からわずかにずれるという癖があります (鍵が「梁 (はり)」として振動するため)。 |
| **セント (cent)** | 音の高さの細かい単位。半音の 100 分の 1。人の耳で「ちょっと高い?」と感じ始めるのが 10〜20 セント程度です。 |
| **チューニングのずれ (tine tuning offset)** | 楽器の個体ごとに、鍵の音の高さが基準からわずかにずれていること。例: 今回テスターさんの 34 鍵カリンバは、ラ (A4) の鍵が基準より 20 セント高いことが測定でわかりました。 |

### 「正解データ」と測定の言葉

| 用語 | 意味 |
|---|---|
| **GT (ground truth / 正解データ)** | ある録音の中で「実際にどの音がいつ弾かれたか」を確認して作った答え合わせ用のリスト。ソフトの成績はこれと照らして採点します。正解データ作りは人間が耳で確認するのが基本ですが、多声で難しい録音は AI が複数の物理的な証拠 (音の周波数の精密測定など) を突き合わせて作る方式も、条件付きで認めています (後述の約束事 16)。 |
| **F1 スコア** | ソフトの成績を 0〜1 で表す点数 (1 が満点)。「弾かれた音をどれだけ拾えたか (取りこぼしの少なさ)」と「出力した音のうちどれだけ正しかったか (間違い出力の少なさ)」の 2 つを 1 つにまとめたものです。 |
| **FN (取りこぼし)** | 実際に弾かれたのに、ソフトが楽譜に出せなかった音。 |
| **FP (誤検出)** | 弾かれていないのに、ソフトが楽譜に出してしまった音。 |
| **飽和 / 非飽和** | ある録音でソフトが満点 (F1 = 1.0) を取ってしまうと、その録音ではもう改善が測れません。これを「飽和」と呼びます。**成績報告には飽和していない録音だけを使う**のがこのプロジェクトの鉄則です (満点の録音を混ぜると成績が実力より良く見えてしまうため)。 |
| **CI95 (95% 信頼区間)** | 測定のブレ幅。録音の本数が限られているため、「真の実力はだいたいこの範囲のどこか」という幅で示します。例:「0.740、幅 [0.617〜0.843]」= 実力はおおよそ 0.62〜0.84 の間。 |
| **current benchmark (現行測定)** | いま手元にある全録音 (非飽和のみ) で測った最新の成績。**このプロジェクトの「公式の成績」はこれ 1 本**と決めました (第 4 期からの新ルール。過去に 2 種類の数字が混ざる事故があったため)。現在値: **非飽和 10 録音で F1 = 0.740、幅 [0.617〜0.843]**。 |
| **baseline (下限記録)** | 録音ごとの「これまでの最低保証成績」。ソフトを変更してこれを下回ったら「壊した」とみなして自動で警告されます。下限は上げる方向にしか動かさないのが原則です。 |
| **corpus (コーパス)** | 評価に使う録音のコレクション。 |
| **local-only (手元だけ)** | 著作権のある曲の録音や正解データは、公開の保管庫に入れず開発者の手元だけに置くこと。例: テスターさんの「ゲゲゲの鬼太郎」の録音は、曲が著作権管理下にあるため手元だけで使います (曲の統計値のみ公開側に記録)。「サリーガーデン」はパブリックドメイン (著作権切れ・自由に使える) なので公開側のコレクションに入りました。 |

### 開発の進め方の言葉

| 用語 | 意味 |
|---|---|
| **スプリント** | 作業のひとまとまり。このプロジェクトでは時間 (1 週間など) ではなく、「**人間が『進めて良い』と判断するまで**」が 1 スプリントの区切りです。 |
| **GO** | 人間 (開発者) による「進めて良い」という明示の承認。AI が勝手に次の段階へ進むことは禁止されています。 |
| **中間ゲート** | 各計画の折り返し地点に置いた検問所。ここで「続けるか・別の計画に切り替えるか・一時停止するか」を人間が判断します。 |
| **planning stock (計画の在庫)** | 承認済みの「実行中の作業」ではなく、順番が来たら取り出す「予定の在庫」。今回の計画は大部分がこの在庫です。 |
| **ガードレール** | 過去の失敗から作った、事故を防ぐための約束事。番号付きで管理しています。 |
| **kill 条件 (打ち切り条件)** | 実験的な改造を始める**前に**、「この数字を達成できなければ打ち切って捨てる」という基準を数字で決めておくこと。後から基準を動かして「成功したことにする」誘惑を防ぎます。 |
| **dual-run (比べ走り)** | 同じ録音を「改造前の設定」と「改造後の設定」の両方で処理して成績を比べる方式。改造の効果を公平に測れます。 |
| **research line (研究路線)** | 成功するか分からない実験的な改造の系統。本体に入れる前に、打ち切り条件・比べ走り・監査という厳重な手順を通します。 |
| **issue / #番号 (チケット)** | 「#209」のような番号は作業チケット (課題やアイデアを 1 件ずつ記録したページ) の番号です。 |
| **merge (取り込み)** | 実験用の別ラインで作った変更を、本体のプログラムに合流させること。 |
| **prod (本番)** | 実際に動いているサービス本体。開発中のものと区別します。 |
| **CI (自動テスト)** | プログラムを変更するたびに、数百件のテストが自動で走って壊れていないか確認する仕組み。 |
| **dogfooding (自家使用テスト)** | 開発者自身が自分のソフトを本気で使ってみて、実際の使い勝手を測るテスト。 |
| **弾き戻し検証** | ソフトが出した楽譜を見て、演奏者が実際に弾き直せるかを確かめる検証。楽譜として本当に役立つかの最終チェックです。 |
| **streaming (リアルタイム処理)** | 録音が終わるのを待たず、弾いているそばから楽譜化を進める方式。将来の目標の 1 つ。 |
| **ブラウザ単独動作 (WASM)** | 録音をサーバーに送らず、手元のブラウザの中だけで楽譜化まで完結させる技術。将来の目標の 1 つ。 |

### AI・体制の言葉

| 用語 | 意味 |
|---|---|
| **agent (エージェント)** | このプロジェクトで作業する AI アシスタントのこと。 |
| **Fable / Opus 4.8 / Sonnet** | Anthropic 社の AI「Claude」の種類 (グレード)。**Fable** = 第 3 期まで主担当だった最上位 AI。契約の関係で 2026-07-07 でいったん使えなくなります。**Opus 4.8** = 第 4 期の主担当を引き継ぐ AI。**Sonnet** = 定型的なプログラム作成を分担する AI。 |
| **Codex (gpt-5.5 / fugu)** | 別会社 (OpenAI 系) の AI。**わざと別会社の AI を「監査役」に固定起用**しています。同じ AI が自分の仕事を自分で監査すると、身内びいき (確証バイアス) が混ざるためです。今回は gpt-5.5 と fugu という 2 種類が監査しました。 |
| **subagent (サブエージェント)** | AI が呼び出す補助 AI。今回の計画評価では、同じ Fable から「AI 実行者の視点」「人間の使い手の視点」「あら探し専門の批判的視点」という 3 人の別視点サブエージェントを立てて、それぞれ独立に計画を評価させました。 |
| **監査** | 作った計画や判定基準を、作った本人以外 (別の AI や人間) が批判的に検査すること。 |

## 2. この計画がどうやって作られたか (承認前の検査のはなし)

この計画の最初の版 (v1) は、主担当 AI (Fable) が契約期限の前日に 1 日で書いたものでした。開発者の指示で、**承認する前に 5 つの独立した目で検査**を行いました:

1. 別会社の AI (gpt-5.5) による監査 — 3 回のチェック
2. もう 1 つの別会社 AI (fugu) による監査
3. Fable 自身の別視点サブエージェント 3 人 (AI 実行者視点 / 人間の使い手視点 / 批判的視点)

この検査で、**本物の欠陥が 3 件**見つかりました:

- **成績の数字の混用**: 計画に書かれていた公式成績 (F1 0.744) は、実は古い集計方式の数字で、最新の正しい数字は 0.740 でした。放置すると以後の「良くなった/悪くなった」の判定がすべて 0.004 分甘くなるところでした。
- **計画 B の測り方の自己矛盾**: 「出力・画面まわりの改善」計画の成果を、画面改善では原理的に動かない数字で測る設計になっていました (しかも過去の自分たちが「この数字は画面改善では動かない」と明記していた数字でした)。
- **録音集めを担当する計画の不在**: このプロジェクトの一番の律速要因 (足かせ) は録音データの不足だと過去に何度も確認されているのに、録音を能動的に集めにいく計画がどこにもありませんでした。

これらを全部直した改訂版 (v2) が本計画です。最後に fugu が「このまま進めて良い。直すべき点はない」と判定し、開発者の事前承認により発効しました。

> **教訓として記録**: 期限直前に 1 人 (1 つの AI) が駆け込みで書いた計画には、自分では気づけない偏りが入り込む。大きな計画は承認前に複数の独立した目で検査する — これを今後の標準手順にしました。

## 3. 今回の承認範囲 — 「全部やって良い」ではありません

この計画には 5 本の計画 × 8 スプリント = 40 スプリント分が書かれていますが、**今回「進めて良い」と承認されたのは、最初の計画 (計画 B) の前半 (B0〜B4) だけ**です。

残りはすべて「計画の在庫」です。各計画の折り返し地点 (中間ゲート) や計画の変わり目で、そのつど人間が中身を見て「次の区間も進めて良い」と承認して初めて動き出します。一度に大きく承認しないのは、状況が変わったときに軌道修正しやすくするためです。

## 4. 計画全体の骨組み

第 4 期は、**独立した 5 本の計画 (B・E・A・D・C) を 1 本ずつ順番に実行**します。おすすめの順番は **B → E → A → D → C** です (理由は第 6 章)。

大事な運用ルール:

- **同時に動く計画は 1 本だけ**。ただし「常設の隙間仕事リスト」(第 5 章の後) はいつでも進めて構いません。
- **各計画の折り返し (4〜5 スプリント目) に中間ゲート**があり、「続行 / 次の計画へ切り替え / 一時停止」を人間が判断します。
- **30 日ルール**: 計画を始めてから 30 日たったら、進み具合に関係なく中間ゲートを強制的に開きます。昔、作業の区切りが形だけになって計画が暴走した反省からのルールです。
- **一時停止 (凍結) の条件**: 「今の AI 体制ではどうしても判断できない具体的な障害」を特定して記録した場合だけ、**最長 30 日**の一時停止ができます。「Fable が戻ってくるまでなんとなく待つ」という理由での停止は**禁止**です (難しい判断を先送りする逃げ道になるため)。

### 成績の数字は 1 本に統一 (公式の物差し)

過去に数字の混用事故があったため、以下の 3 つを明確に区別し、**公式の成績は 1 番だけ**と決めました:

| 物差し | 現在値 | 何に使うか |
|---|---|---|
| 1. **現行測定 (公式)** | 非飽和 10 録音で **F1 = 0.740、ブレ幅 [0.617〜0.843]** (測定: 2026-07-06 22:25 日本時間) | 進歩したか・後退したかの判断はすべてこれ。最新のプログラムで測り直した値。**この数値はすぐ古くなる — より新しい測定があればそちらが正** |
| 2. 第 3 期末の凍結値 | 11 録音で F1 = 0.744 | 過去の判定に使った歴史的な記録。**今後の比較には使わない** |
| 3. 自動テスト用の下限 | 公開録音 6 本で 0.825 | プログラム変更で成績が壊れていないかを自動で見張る下限。公式成績ではない |

(1 と 2 の録音数が違うのは、1 本の録音でソフトが満点を取って「飽和卒業」したため。卒業した録音は成績計算から外れます。)

### 前の期 (第 3 期) から引き継いだ到達点

- **「鍵 1 本ずつの物理追跡」機能が本体入り**: カリンバの鍵ごとに音の波の位相 (波のタイミングのずれ) を追跡し、「同じ鍵をもう一度弾いた」のを残響と区別して拾う機能。3 回の厳格な判定 (事前に決めた打ち切り条件をすべてクリア) を経て本体に取り込まれました。
- **他の人の演奏の録音が 7 本集まった**: これまで開発者本人の演奏ばかりでしたが、テスターさんの録音が加わり、「他の人・他の楽器への対応 (汎化)」に取り組む条件が整いました。**ただし正直な注記**: 集まった録音はよく知られた曲・17 鍵の楽器に偏っていて、34 鍵の録音は 1 本だけです。「汎化ができた」のではなく「汎化に投資する資格ができた」段階です。
- **「精度がボトルネック」という重要な仮説がまだ 1 回しか検証されていない**: 自家使用テストの結果「楽譜の修正が大変なのは、画面の使い勝手よりソフトの精度のせい」という判定が 1 回出ていますが、たった 1 回です。計画 B の最初の仕事はこの再検証です。

### 新しい AI 体制が最初にやる受け入れチェック

第 4 期から主担当 AI が交代します (Fable → Opus 4.8)。引き継ぎ事故を防ぐため、新しい AI は作業を始める前に、次の 6 点を**自力で**説明・実行してみせることが義務です (できなければ引き継ぎ資料の修理が先):

1. 現在地の説明 (どの計画のどこにいるか)
2. 上記 3 つの成績の物差しの区別と、公式成績の測り直し実行
3. 報告の禁止ルール (飽和録音を混ぜた成績を公式に使わない等) と約束事 15〜18
4. 手元だけのデータ (著作権曲の録音・正解データなど) がどこにあり、何が公開不可かの説明
5. 補助 AI (Sonnet) への仕事の頼み方のルール (仕様を文書で確定してから頼む・検収条件を明記する・調べ物には時間制限を付ける)
6. **このチェック結果を作業記録ページ (チケット #212) に書き残す**

## 5. 5 本の計画の中身

### 計画 B: 出力・使い勝手 — 楽譜を「使える」ものにする 【最初に実行】

**目的**: ソフトが出した楽譜を、演奏者が実際に使える形にすること。ただし最初の仕事は機能追加ではなく、**「精度がボトルネック」仮説の再検証 (B0)** です。全計画の実行順序がこの仮説に乗っているのに、検証が 1 回しかされていないためです。

**成果の測り方 (今回の検査で全面的に直した点)**: 以前の計画は「機械が見積もった修正量」という数字で成果を測る設計でしたが、この数字は画面の改善では原理的に動きません。そこで、**実際の操作回数・修正にかかった時間・弾き戻しの成功率**という「人間の体験の数字」で測ることにしました。数字の合格ラインは測る前に人間と合意して固定します (後から都合よく解釈するのを防ぐため)。

| 段階 | やること | 担当 | 確度 |
|---|---|---|---|
| B0 | **仮説の再検証**: 自家使用テストと弾き戻し検証をあと 2〜3 回 (長めの曲・別の難易度で)。測る前に合格ラインを合意。**結果ごとの進路も事前に固定**: (い) 粗い楽譜で十分と出た → 計画の順番を組み直す / (ろ) やはり精度がボトルネック → チケット #209 だけ仕上げて計画 E や A へ早めに切り替え / (は) 出力改善に効果の余地あり → B1〜B4 を続行 | O+H | A |
| B1 | 作業チケット #209 の仕上げ: 「同じ録音の認識をやり直しても記録が二重にならない仕組み」の画面側 (やり直し結果の切り替え表示・古い結果への注意表示など)。検査済みの変更を本体に取り込み、本番へ反映 (**反映前に、この開発機固有の手順書を必ず読むルール**) | O+S+H | A |

### 計画 A: 楽器・環境への調整 — 「他の人のカリンバ」で動くように 【3 番目】

**目的**: いまのソフトは開発者の 17 鍵カリンバに一番よく合っています。これを、**楽器の個体差・録音環境・奏者の違いに自動で合わせられる**ようにする計画です。

**正直な注記**: この計画は主に「将来の他のユーザー・他の楽器」への投資で、**開発者本人の 17 鍵での体感が良くなるのは後半 (A5) 以降**です。

**根拠となる発見**: テスターさんの 34 鍵カリンバの録音を分析した結果、(1) ラの鍵が基準より 20 セント高い個体差がある、(2) 34 鍵は半音が全部あるため「ある鍵の倍音が別の実在する鍵の音の位置にちょうど着地してしまう」(例: ラの第 3 倍音がミの鍵の位置に鳴る) という 17 鍵にはない紛らわしさがある、と分かりました。ソフトが楽器ごとのずれを自動測定して補正すれば、この紛らわしさを大きく減らせるはずです。

**慎重さが必要な点**: この分析の土台になった録音 (ゲゲゲの鬼太郎) の正解データは AI が裁定したもので、著作権の関係で第三者が独立に検証できません。そこで**「1 音ずつ孤立して弾いた録音」(計画 E2 のキットで依頼) による独立確認を、本格的な改造 (A3) の前提条件**にしています。

## 6. なぜこの順番 (B → E → A → D → C) なのか

| 順 | 計画 | 理由 |
|---|---|---|
| 1 | B (出力・使い勝手) | 最初の仕事 B0 が「全順序の前提になっている仮説 (精度がボトルネック) の再検証」だから。また、ソフト本体を触らないので、新しい AI 体制の肩慣らしとして事故リスクが最小。着手できるチケット (#209) が既に開いている |
| 2 | E (データと測定) | 録音は「依頼してから届くまで」の待ち時間が長いので、依頼キットの発射は早いほど得。後続の A と D が使う録音と検証の仕組みは E が用意する |
| 3 | A (楽器への調整) | 「他の人の楽器で動く」への投資。E の成果 (孤立音録音・正解データ検査) が安全装置として先に必要 |
| 4 | D (取りこぼし攻略) | 本体の実験的改造は、別会社 AI の監査体制が一度実走してから。ただし分類作業 (D1) は最初から隙間仕事で進める |
| 5 | C (リアルタイム化) | 「多くの人が使えること」が先、という方針の帰結 |

- 順番の変更は人間の判断でいつでも可能です。**B0 の再検証で「粗い楽譜でも十分」という結果が出たら、直ちに順番を組み直して提案**します。
- **Fable (前の主担当 AI) が戻ってきたときの合流地点**も決めてあります: 各計画の中間ゲートと計画の変わり目です。「戻ってくるまで待つ」ための停止は禁止です。

## 8. 約束事 (ガードレール) — 過去の失敗から作った安全ルール

第 3 期までの約束事 14 本 (「満点は成功ではなく飽和のサイン」「実験は打ち切り条件を先に数字で固定」など) はすべて継続。第 4 期の追加・強化分:

- **15. 承認の単位**: 計画の開始・切り替え・停止は人間の承認のみ。承認の対象は常に「次の中間ゲートまで」に限る。
- **16. AI が正解データを作るときの条件 (強化)**: 人間の耳で裁定できない録音 (多声など) は AI が物理的な証拠で正解データを作って良い。ただし — (a) 複数の証拠の裏付けと記録が必須、(b) 人間の判定を覆すときは明示報告、(c) 著作権未確認の録音のデータは手元だけに保管、(d) **採点対象のソフト自身の出力だけを根拠にしない** (身内の答え合わせを防ぐため、外部の独立した音採り AI を含む 2 系統以上の証拠が必須)、(e) 調整に使った録音は同じ改造の最終検証から除外、(f) 裁定の約 1 割を抜き打ち検査用に保存、(g) **AI 裁定の正解データだけに基づく設計判断は「暫定」止まり** — 独立に検証できる録音で確認するまで正式ルールにしない。
- **17. 満点卒業の手続き (強化)**: 録音が満点になって成績計算から卒業するときの基準更新は、正式な手続き (人間の承認 + 経緯の記録) を踏む。更新後は最新の測定値だけが公式で、**古い数字を比較に使い続けることを禁止** (今回の v1 の混用事故を反面教師として明記)。
- **18. 30 日ルール (新設)**: 計画開始から 30 日で中間ゲートを強制発動。停止 (凍結) は期限付き (30 日以内) のみ。

### 計画を見直すきっかけ (再計画トリガー)

次のことが起きたら、進行中でも立ち止まって計画を見直します:

- 新しい録音が届いた → 何よりも先に受け入れ処理
- 記譜方式の判断 (チケット #202) が出た → 計画 B2 を即座に具体化
- B0 の再検証で「粗い楽譜で十分」と出た → 実行順序を全体的に組み直し
- Fable (前の主担当 AI) が復帰した → 合流地点のルールで判断 (待つための停止は禁止)
- 公式成績が 2 計画連続で動かなかった → 計画の在庫全体を作り直し
- 新しい AI が受け入れチェックに失敗した → 引き継ぎ資料の修理を最優先

## 10. 中長期の展望 (この先のマイルストーン)

| マイルストーン | 内容 | 現在地 |
|---|---|---|
| M1: 汎化 | 他の人・他の楽器・他の録音環境で使えること | **投資する資格が整った段階** (計画 A が実装本体、計画 E がデータ供給) |
| M2: リアルタイム | 弾きながら楽譜が出てくること | 計画 C の中間ゲートで進入判断 |
| M3: ブラウザ単独 | 録音をどこにも送信せず手元で完結すること | 計画 C の後半。外部 AI をソフト本体に混ぜない方針は不変 |
| M4: 出力 | 楽譜として本当に使えること | 計画 B が実測開始 (物差しは操作回数・時間・弾き戻し成功率) |
| M5: 公開 | プロジェクトを外に開くこと | 変更なし (M1 が先) |

基本方針:「M1 (誰でも使える) が本丸、M4 (使える楽譜) が製品の顔。M1 の前に M2/M3 に深入りしない」。
