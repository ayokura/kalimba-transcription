## 2026-07-04: 認識器の引き上げへ再集中する (計器修理を前提に)

**判断**: 「今使ってもらう」ための binding constraint は認識器の下限品質と評価し、
第 2 期計画 ([sprint-plan-2026-07b.md](sprint-plan-2026-07b.md)) の中心を
「認識改善を測定可能にする (計器修理) → 引き上げる」に置く。

**経緯**: それ以前の判断の流れは — (1) 認識器が一定品質に達したと判断し、
編集 UI (候補提示による修正コスト削減を含む) とアウトプットの設計へ軸足を
移した → (2) テスター向け UI を作り実地録音を取ったところ、うまく動かない
ケースが複数出た → (3) 原因を分解すると (a) ブラウザ音声処理 (voice
processing) の混入や低信号録音という **capture 側の問題** と、(b) **認識器
自体の甘さ** の混合だった。

**根拠**:
- (a) capture 側は voice-processing 無効化 (2026-06-27 prod)、録音後の
  聴き直し UI、音量警告調整でほぼ解消済み → 以後の失敗は (b) の比率が上がる
- (b) 側の実測: 唯一の非飽和自由演奏 17ea7626 で F1 0.863 / hard miss 7。
  hard miss (候補すら無い見逃し) は編集 UI の守備範囲外で、UX では救えない
- 編集 UI 側 (picker / ワンタップ置換 / corrections 頑健化) は第 1 期までに
  一定の完成を見ており、限界費用が認識側より高い

**留保**: 「自由演奏に対して認識がどれだけ足りないか」は n=1 でしか測れて
いない。第 2 期前半の計器修理 (非飽和 held-out の拡充) は、引き上げの前提で
あると同時に「認識が本当に律速か」の検証でもある。用途の再定義 (練習の鏡
なら粗い転写で足りる等、テスターインタビューで判明しうる) はこの判断を
覆しうる反証として明示的に残す。

**影響**: 第 2 期のレーン構成 (corpus/計器が最上位)、outcome ゲート
(非飽和 held-out n≥2→3→5)、編集 UI 系は triage-first (認識の弱点を前出し
する形) に限定して継続。
